最後に「再 render = 悪」という思い込みをほどきます。

### render phase と commit phase の違い

| Phase  | 何をするか                                  | コスト                                   |
| ------ | ------------------------------------------- | ---------------------------------------- |
| render | 関数コンポーネントを実行して VDOM を作る     | 純関数的であるべき（副作用を書くと Strict Mode の二重実行で破綻する） |
| commit | 差分があれば実 DOM に反映、layout effects 実行 | DOM mutation があれば重い                |

「再 render された = DOM が動いた」ではないことに注目してください。
この Lab の可視化カードには **DOM mutation 件数** のカウンタもあります。
ボタンを押して total renders が増えても、**画面に差がなければ mutation は 0 のまま** です。

### 観察のポイント

- memo を付けていない状態で「state を更新」を押す
- total renders はクリック数だけ増える
- DOM mutation 件数は 0 に張り付く

### 何を判断基準にすべきか

- プロファイラで **遅いと測れた** 箇所にだけ memo を使う
- 遅くない場所は、再 render を恐れない（commit が軽ければコストは小さい）
- 大規模 list や重い計算の最適化は別問題（virtualization / useMemo）
