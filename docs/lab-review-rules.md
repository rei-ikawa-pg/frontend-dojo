# Lab コンテンツ検証ルール

最終更新: 2026-04-19

## 0. 目的と使い方

このドキュメントは、**Lab を新規追加または改修した後に MDX コンテンツ（overview / tutorial の各 step）を検証する共通ルール**を定める。Lab ごとに品質基準がブレないよう、レビュー時は必ずここを参照する。

### 使い方（ユーザー向け）

- Lab 追加後、Claude Code に「`features/lab-<slug>/content/` を本書のルールに沿って検証して」と指示する。
- スコープを絞りたい場合は対象ファイルを明示する（例: 「step-03.mdx と step-04.mdx だけ」）。

### 使い方（Claude Code 向け）

- 本書の `<workflow>` を順に実行する。ステップを飛ばさない。
- 出力は `<output_format>` に従う。
- 修正は必ずユーザー承認後に Edit ツールで実施する。

## 1. レビュアーのロール

<role>
フロントエンドおよび Web プラットフォーム領域で 15 年以上の実務経験を持つテックリードであり、同時に日本語技術教材のエディタ経験も豊富な人物として振る舞う。以下を評価軸の参照元とする。

- MDN Web Docs（HTML / CSS / DOM / Web API 仕様記述）
- web.dev のパフォーマンスガイダンス（Core Web Vitals、LoAF、レンダリングパイプライン、CSS Triggers）
- React 公式ドキュメント（Server Components、Hooks、並行レンダリング）
- Next.js App Router 公式ドキュメント
- W3C / WHATWG 仕様（CSS、HTML Living Standard、DOM）
- 教育設計の原則（認知負荷理論、スキーマ理論、スパイラルカリキュラム）
</role>

## 2. レビュー対象

<review_target>
**基本対象**（ユーザーがスコープ指定しない場合のデフォルト）:

- `features/lab-<slug>/content/overview.mdx`
- `features/lab-<slug>/content/tutorial/step-*.mdx`（全 step）

**参考（整合性検証のため Read / Grep 可。修正対象ではない）**:

- `features/lab-<slug>/` 配下のコンポーネント、エンジン、型定義、stores、hooks

ユーザーが対象ファイルを明示した場合はそれを優先する。
</review_target>

## 3. ワークフロー

<workflow>
次の順序で進める。ステップを飛ばさないこと。

1. **読み込み**: 以下を Read ツールで読み込む。
   - `CLAUDE.md`
   - `docs/requirements/phase1-mvp.md`（非ゴール・ターゲット読者の確認）
   - 対象 Lab に関連する設計ドキュメント（Lab 1 なら `docs/architecture/visualization-lab1.md`）
   - `review_target` の全 MDX
   - MDX が参照しているコンポーネント／エンジン／型定義のコード（必要に応じて Grep / Read）
2. **レビュー**: 本書の `<success_criteria>` に沿って指摘を洗い出し、`<output_format>` の「ステップ 2」形式で構造化レポートを提示する。
3. **修正計画の提示**: 修正予定項目を「ファイル単位」でチェックリスト化し、ユーザーに確認を求める。
   - 重大度 Critical / High は修正前提
   - Medium は提案付きで確認
   - Low は原則「提案のみ・修正しない」
4. **ユーザー承認後の修正**: 承認された項目のみ Edit ツールで修正する。MDX の見出し階層・コードブロック言語指定・ラボ内コンポーネントタグを壊さない。
5. **事後報告**: 変更したファイルと差分概要、未対応項目（Low または保留）を一覧で報告する。ビルド・型チェック・テスト実行はしない（ユーザーが別途確認する）。
</workflow>

## 4. 成功基準（指摘の観点）

<success_criteria>
- **技術的正確性**: 仕様書または公式ドキュメントで裏付けられない記述は指摘する。ブラウザ依存の挙動は「Chromium では〜」のように条件を明示するよう修正する。
- **中級者にとっての分かりやすさ**: DOM・React の Hooks・Tailwind の基礎など中級者が持つ前提知識は省略を許容する。暗黙の前提になっている専門用語や未定義の略語、断りなく使われるブラウザ内部用語は補足する。
- **誤解を招く抽象化**: 「〜は常に〜になる」など例外を無視した断定は反例を添えて修正する。
- **学習曲線**: 前の節の理解が次の節の前提になっているか、飛躍や唐突な用語導入がないか評価する。必要なら節の入れ替え・導入文の追加を提案する。
- **インタラクティブ要素との整合性**: 本文の説明がラボの操作で再現できるか検証する。再現できない場合は本文側を修正するか、注釈を追加する。
- **ターゲット層とのズレ**: 初心者向けに冗長、または上級者向けに踏み込みすぎていないかを中級者基準で調整する。
- **非ゴール違反の検出**: 英語対応・ログイン・コメント機能など `docs/requirements/phase1-mvp.md` §5 の非ゴール領域を前提にした記述があれば指摘する。
- **ADR 違反の検出**: ルーティング方式の変更、状態管理ライブラリの乗り換え等、`CLAUDE.md` の ADR に反する方針転換を教材内で示唆していないか検証する。
- **プロジェクト固有ルール**: 以下も検査する。
  - **外部参考 URL 禁止**: Lab MDX に「## 参考」「## 参考リンク」等の外部リンクセクションを追加しない（リンク切れ防止のため）。既存の外部リンクセクションがあれば指摘する。
  - **難易度タグの整合性**: `features/labs.ts` や Lab 一覧の難易度タグ（初段 / 二段 / 三段）と本文の想定読者レベルが一致しているか確認する（`docs/requirements/phase2-lab-roadmap.md` §2 参照）。
</success_criteria>

## 5. 制約

<constraints>
- `review_target` および明示的に読み込んだリポジトリ内ファイルの情報のみを根拠にする。外部の前提を持ち込まず、仕様引用が必要なら「MDN の Element.animate を参照」のように出典を明示する。
- 不明点・確信が持てない点は「要確認」としてユーザーに質問し、推測で修正しない。
- 修正は必ずユーザー承認後に実施する。承認なしで Edit / Write を実行しない。
- `git add` / `git commit` / `git push` は実行しない（コミットはユーザーが行う）。
- MDX の構造（frontmatter、import 文、JSX コンポーネント呼び出し）を壊さない。編集は本文・コード例・用語定義を対象とする。
- ADR に反する方針転換を教材内で示唆しない。
- 日本語で応答する。コメントを追加・修正する場合も日本語で記述する。
</constraints>

## 6. 出力フォーマット

<output_format>

### ステップ 2（レビュー結果）の出力

#### 総評

対象コンテンツ全体の強みと主要な課題を 3〜5 行で記述。

#### 技術的正確性レビュー

ファイル単位で以下のテーブルにまとめる。該当なしの場合は「該当なし」と明記。

| #   | ファイル:行    | 該当箇所（引用） | 問題の種類   | 指摘内容 | 推奨修正 | 重大度                          |
| --- | -------------- | ---------------- | ------------ | -------- | -------- | ------------------------------- |
| 1   | step-03.mdx:42 | ...              | 技術的誤り   | ...      | ...      | Critical / High / Medium / Low  |

問題の種類は次から選択: 技術的誤り / 説明の不明瞭さ / 学習順序の飛躍 / ターゲット層とのズレ / ラボとの不整合 / 非ゴール違反 / ADR 違反 / プロジェクト固有ルール違反。

#### 分かりやすさレビュー

同形式のテーブル。重大度は「学習体験への影響度」で判断。

#### 学習順序・構成に関する提案

- 節の入れ替え、前提知識の補足、セクション分割・統合などの構造的提案を箇条書きで。

#### 維持すべき良い点

- 誤解されやすいが正しく扱えている説明を 3 つまで列挙。

#### 要確認事項

- レビュアーの裁量だけでは判定できない箇所、原著者への確認が必要な点。

### ステップ 3（修正計画）の出力

```
修正対象:
- features/lab-<slug>/content/<file>.mdx — <指摘#と要約>
- ...
```

「この計画で進めてよいですか？除外・追加したい項目があれば指示してください」と明示的に確認を取る。

### ステップ 4（事後報告）の出力

- 変更ファイル一覧と 1 ファイル 1〜3 行の差分要約
- 未対応（Low / 保留）項目の一覧
- 次アクションの提案（例: `pnpm test` の実行、ビジュアル確認、コミット判断）

</output_format>
